# Design notes

为什么这样写，以及踩过什么坑。**每一条都是实测得到的**，不是推测。

---

## 1. 为什么先做情报层，再决定要不要下载

视频有三个硬伤：**不能搜索、不能摘录、不能对比**。

所以「这门课值不值得下」这个问题，不能靠下载完再判断。情报层（`cli/bili.mjs`）的四个命令加起来不到一分钟，就能给出分P结构、总时长、互动数据和字幕可用性。反过来做（先下载再评估）会浪费几十小时机器时间。

**顺序即成本。** 这是整个流水线分层的理由。

---

## 2. 校验为什么必须是三层

批量下载里真正会发生的故障，和直觉不一样。

**直觉以为的故障**：文件没下下来、文件是 0 字节。
**实际发生的故障**：文件在，体积正常（几 MB 到几十 MB），**内容是随机字节**。

```
正常 : 0000 0024 6674 7970 6973 6f6d   ....ftypisom  合法 MP4
损坏 : 650c d2ee 1697 10e3 ad4e 3251   随机字节
```

在损坏文件里搜 `ftyp` 和 `moov`（MP4 必需的原子），**从头到尾一个都找不到**。所以它不是「下了一半的 MP4」，而是内容根本不是目标音频。

这类文件的特点是：**体积完全正常**。任何只看存在性、数量、字节数的检查都抓不到它。只有打开容器头做时长探测才能发现。

### 由此得到的操作结论

- 批量下载后**一定要跑一次时长探测**，不能只做数量校验
- 损坏率不高但**分散**，没有集中规律，符合长批次下载中的间歇性 CDN 问题
- 修复要**定点重下**，不能重跑整批 —— 见下一条

---

## 3. 为什么重下必须定点，不能重跑下载脚本

下载脚本的跳过判据是**文件名完全相同**。

而规范化那一步已经把文件名从「合集标题」改成了「分P标题」。所以重跑原脚本时，它看到磁盘上的文件名和自己要生成的名字**对不上**，于是：

> 它会把整个库**全部重下一遍**。

所以 `cap redownload` 单独存在：读 `manifest.json`，只取 `status != ok` 的条目，从文件名前缀取分P序号，从路径取课程标识，用 `--playlist-items N` 精确重下那一个。

**这是「流水线顺序」造成的耦合**：一旦中间步骤改变了文件名，前面步骤的幂等性就失效了。

## 4. 指纹比对的参数，两个都踩过

目标是判断「同一讲的两个上传版本是不是同一段录音」。标题没法用（措辞完全不同），只能比音频。

做法：时长中点取窗口 → 单声道 PCM → 20ms 粒度 RMS 包络 → 归一化互相关。

### 坑一：分析窗太短

先用 40 秒窗，发现**不相关的内容之间也会出现 0.2–0.3 的相关系数**。包络太短，区分度不够。

改成 **90 秒**。

### 坑二：对齐搜索窗太窄（更隐蔽）

两个版本时长差 14 秒（片头被剪），那么**时长中点处的偏移约 7 秒**。

搜索窗只给 ±3 秒时，同一段录音的最佳对齐点落在窗外，于是取到了窗内的最大噪声值 —— **实测 0.2457**，看起来就是「不相关」。

差一点据此得出「这两个版本内容不一样」的错误结论。

改成 **±25 秒**后：

| 比对 | 相关系数 |
|:--|:--|
| 同一讲的两个版本 | **0.9983** |
| 不同讲（负对照） | **0.1948** |

放宽参数后重跑全部 13 对：**0.9626–1.0000，均值 0.9897**（其中 2 对为 1.0000）。负对照仍是 0.19，判据可区分。

### 教训

**阈值没有绝对意义，必须用负对照校准。** 没有「不同内容」这一组的分数，你无法判断 0.2457 到底是「不相关」还是「相关但没对齐」。

`tests/test_fingerprint.py` 把这两条固化成回归测试：AC19 直接断言「窄窗口下必须得到 < 0.5」，任何人把参数改回去都会红。

### 附带发现

比对中还发现字幕版在中点处普遍比正式版**早约 4.7 秒**，说明片头片尾有剪辑，但讲课内容一致。这正是「中点偏移」的实证。

## 5. 为什么剔除只移动、不删除

一次批量下载要跑一小时。多留一份冗余文件的代价是几百 MB。

**这个不对称决定了默认动作必须是可逆的。**

所以：

1. `cap classify` 只产出清单，等确认
2. `cap quarantine` **移动**到 `<root>/_quarantine/`，保留原层级
3. 写 `_move_log.json`（逐条 src/dst）+ `RESTORE.md`（人读的还原说明）
4. 执行后做**守恒校验**：资料库剩余 + 隔离区 = 原总数
5. `cap restore` 随时一键还原

守恒校验是这套设计里最关键的一步 —— 它把「我以为没丢东西」变成「数字对得上」。

### 配套约定：`_` 前缀目录不参与统计

`_manifest/` 和 `_quarantine/` 都以 `_` 开头，扫描时跳过。

不这样做的话，剔除后重跑校验得到的数字会**把隔离区的文件也算进资料库主体**，看起来像什么都没剔除。

## 6. 分类规则为什么是数据，不是代码

最初规则是硬编码在 Python 里的正则表，内容是某个具体考纲的术语。

问题：换一个科目、换一套考纲，就得改代码。

改成 `cap/default_rules.json` 之后，新增分类维度不需要碰 Python。`tests/test_classify.py::test_rules_are_data_and_can_be_overridden` 验证了覆盖行为。

**一条重要的取舍**：变体配对（AC14）在时长或数量对不上时**宁可漏判，不误判**。因为误判的代价是删掉了不该删的内容，而漏判只是多留一份文件 —— 和上面第 5 条的判断一致。

## 7. 转写层的三个细节，都是血泪

### 7.1 行缓冲是必须的

每段字幕约 50 字节，Python 默认缓冲 8 KB。不加 `buffering=1` 的话，**跑到 30% 时 `.srt` 仍然是 0 字节**，看起来像卡死。

（当时真的以为模型下载失败，去翻 HuggingFace 缓存才发现模型早就有了。）

注意是 `buffering=1`，**不是** `line_buffering=True` —— 后者是 `io.TextIOWrapper` 的参数，`open()` 不接受，会直接抛 `TypeError`。

### 7.2 完成标记必须是 `.json`，不能是 `.srt`

中断时 `.srt` 也是非空的。用它当「已完成」的标记，下次会**跳过一份其实没做完的文件**。

`.json` 只在所有段落写完后落盘，是唯一可靠的完成标记。AC27 固化了这条。

### 7.3 长任务不能接管道

```bash
# ✗ 下游一断，python 收到 SIGPIPE 直接被杀，前面几十分钟全白跑
python transcribe.py audio/ transcripts 2>&1 | tail -40

# ✓ 重定向到日志文件
python transcribe.py audio/ transcripts > transcribe.log 2>&1
```

实测踩过：37 分钟的转写跑到一半进程消失，`.json` 没生成、`.srt` 停在缓冲 flush 的那一点，**整轮白跑**。

## 8. 自动转写产出的是原料，不是成品

这一条不是代码问题，是流程问题，但影响最大。

小模型在中文技术内容上会把专有名词几乎全搞错，而且**把术语写进 `initial_prompt` 也修不回来** —— 断句和标点会明显变好，专有名词错误一个都没修掉。

所以正确流程是两段：

```
① 机器转写  → 转写原文.md   可检索、带时间轴，但专有名词不可信
② 人工校对  → 校对要点版.md  真正可引用、可复习的成品
```

**分工**：机器负责「不漏」，人负责「不错」。

**不要跳过第 ② 步就直接用转写原文复习。** 一份写着错误术语的笔记，复习时会把错误概念记牢 —— 比没有笔记更糟。

这是整条链路里唯一无法完全自动化的环节，也是它的价值所在：机器把 37 分钟的「听」压缩成几分钟的「读」，人只需要在「读」上花时间。

## 9. 一个通用的编码教训

**默认参数里不要写 `sys.stdout` / `sys.stderr`。**

```python
# ✗ 在导入时绑定，之后重定向 sys.stdout 不会生效
def run(path, log=sys.stdout): ...

# ✓ 在调用时解析
def run(path, log=None):
    log = log or sys.stdout
```

这个 bug 的表现是：输出明明打出来了，但测试里的输出捕获拿到空字符串。**它能跑，只是不能被测试** —— 这类 bug 最难发现。

## 10. 一个「修了一半」的修复，比没修更危险

元数据 CLI 里的时长格式化函数 `fmtDur()`，被修过两次，第二次才对。这个案例值得单独记，因为它演示了一类**会伪装成已修复的 bug**。

### 事实

搜索接口返回的 `duration` 是字符串，语义是 **`<总分钟数>:<秒>`** —— 分钟数**没有 60 上限**，多 P 合集里能到 4 位。而详情接口返回的是**秒数**。

```
搜索接口  "1349:25"  →  1349 分 25 秒  = 80965s  = 22:29:25
详情接口  80965
```

用 8 条样本把两者交叉核对，**8/8 完全吻合**，语义确认无误。

### 两次修复

| 版本 | 实现 | 结果 |
|:--|:--|:--|
| 初版 | 只按秒数处理 | `Number("12:34") === NaN` → **全部 `0:00`** |
| 第二版 | 字符串直接原样返回，但正则限制冒号前 **1~2 位** | 短视屏正常（`19:57`），**长合集仍 `0:00`**（`1349:25` 不匹配正则） |
| 第三版 | 分钟位放宽到 `\d{1,5}`，保留 `时:分:秒` 防御分支 | 全部正确 |

### 为什么第二版危险

第二版**第一眼看是对的**：搜索一次，结果里 `19:57`、`7:45` 都正常显示了。

问题在于它只覆盖了「分钟数 ≤ 2 位」的数据 —— 也就是短视频。而**恰恰是这个仓库最关心的对象（几十小时的多 P 课程合集）全部静默归零**。如果不拿长合集样本去验，这个半对的修复会一直留着，而且看起来比初版好得多。

### 可复用的做法

1. **格式化函数的测试样本必须覆盖边界**，尤其是「超出直觉范围」的值（三位数分钟、四位数分钟）。只测 `12:34` 这种典型值等于没测。
2. **必须和独立来源交叉核对**。这里的做法是把搜索串换算后与详情接口的秒数比对 —— 单看一侧的显示值，「看起来对」和「实际正确」无法区分。
3. **给回归写一条「不得归零」的显式断言**，而不只是断言正确值。错误症状是归零，那就把归零单独钉死。
4. **负向验证要能指出「哪几条会红」**。把旧实现放回去跑一遍，实测 8 条里红 5 条，而「两位数分钟」那条**照样绿** —— 这条绿的测试正是当初骗过我的原因。如果负向验证是「全红」，反而说明测试写得太粗，定位不到问题边界。

> 这和本仓库 `tests/test_fingerprint.py` 里那条假阴性回归测试是同一个思路：
> 参数调窄时，同一段录音被判成「不相关」（相关系数 0.2457）。
> **把「已知会错的配置」固化成测试**，比只测正确路径有价值得多。
